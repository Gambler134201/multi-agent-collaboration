# 有限并行：候选行为与验证边界

2026-10-25 源码候选：有限调度、四个执行端的工作区接线、收尾协调及正式集成入口已接入。
**尚未部署到日常运行目录。** 上述为2026-10-25的接续记录；2026-10-26已实际验证Pi/DSH/ZCode不同项目三端并发，以及Pi＋DSH同项目独立副本并发（原生区间重叠40.304229秒）与受控集成。后续阶段正确使用集成基线，但两条错误测试预期由主脑接手修正后final_accepted，原失败保留。同模型互斥/唤起有观测，两项交付被保护拒绝，其中一项已离线复现为过滤参数误判，尚未修复，不称整体排队验收通过。阶段存储兼容路径、正式入口和GUI限制见[首轮验收记录](RELEASE_20261103.md)；不能将源码结果等同生产部署。

## 当前行为

- `max_parallel_tasks` 默认 **1**，可保存 1 至 8；界面提供相同的完整范围。
  线程池上限 8 只是调度容量；每项任务必须先在一个锁内拿齐资源，实际运行量受设置约束。
  降低上限不取消已运行任务，开关、模型、权限、金额与次数限制不随升级改变。
- 同模型、相同公开后端身份、同一 WorkBuddy profile 或 ZCode 安装通道互斥；
  以不同模型名连接同一后端不能取得额外容量。`resource_group` 只能增加归并锁。
  未知后端取得全局独占屏障，已知后端共享该屏障，避免未知账户与已知账户重叠。
  任意域名/IP 别名不能全部自动识别；明确共享资源应使用同一公开连接或额外归并组。
- 同一项目的隔离工作区任务可并行；未隔离编辑任务取得独占项目占用，不能与它们重叠。
  非 Git 项目不自动初始化 Git；跨项目且后端独立的任务仍可受全局上限调度。
- 记录、会话与索引文件归原项目；索引描述执行副本。DSH/Pi 仅能直接读取本任务的
  controller context，不能借此写记录、通过终端访问记录或读取其他任务上下文。
- 执行器 `completed` 后，控制器还需提交成果与释放资源。`controller_finalization`
  为 pending 时不通知正常完成、不允许验收、整改或创建交接；异常为 attention。
  原生会话关闭或子进程身份未知时保留资源，不靠超时清空。
- 原责任主脑可调用 `brain_finalize(request_id, task_id)` 显式核对收尾；普通面板的
  对应操作仅适用于非主脑拥有的任务。它不调用模型、不重发执行，不能重新提交已验收
  或已 settled 的成果。中断任务的原执行状态保留，主脑接管仍需逐条独立证据。
- `brain_integrate(request_id, task_ids, checks)` 只接收原责任会话、同项目/目标、已逐条
  独立验收且收尾完成的任务。固定提交 ID，在集成副本运行参数数组形式的检查，保留副本。
  检查失败或修改受版本管理的成果不能算通过；检查通过也不会自动验收或覆盖用户原树。
  请求超时或返回未知时，用原 `request_id` 调用 `brain_request_status` 只读查询，不重发。
- 交接重新绑定真实记录、工作区、分支 HEAD、冻结提交及文件哈希。哈希描述真实文件
  字节，支持 CRLF；工作区缺失、锚点漂移、收尾未确认均拒绝，不退回原树或仅凭 Git 对象。
- 验收同时保存任务、范围与成果提交的绑定。复制其他任务的验收记录或验收后换掉提交都拒绝。
  主脑最终验收会在本任务副本冻结接管修复，保留原执行失败和整改次数；不会提交用户原树。
- 阶段串行依赖从已验收的前置提交建立副本，避免只带摘要却从旧代码开始。
  多个独立前置分支没有共同的已整合基线时拒绝派发；需先集成、独立验收并明确应用成果。

## 已实现

**任务工作区隔离（`task_workspace.py`）**

- `inspect`：只读资格检查。项目必须是 Git 仓库根目录且能解析 HEAD 基线；
  非 Git 项目保持串行，绝不自动 `git init`；仓库子目录初版不隔离并说明原因。
  用户有未提交改动时只记录 dirty，不阻止隔离（基线是 HEAD 提交，用户工作树始终不被触碰）。
- `prepare`：为单个任务创建 `modeldesk-task/<task-id>` 分支和独立 worktree。
  工作区放在项目旁的 `<项目名>-task-workspaces/<task-id>`，不在项目树内、
  不在 `.model-desk` 内。同一任务标识重复创建、分支复用、非法标识、坏基线一律拒绝。
- `status` / `release`：release 只删除干净的工作区；有未提交成果时拒绝并列出
  清单（成果保留待人工核对）。任务分支始终保留，直到集成验收决定其去重。
  残留元数据只报告并按需 prune，不自动清理。
- `precheck_merge`：任务分支两两 `git merge-tree --write-tree`，纯对象库操作，
  不改任何工作树和索引；输出逐对冲突文件。
- `integration_workspace` / `trial_merge` / `trial_sequence` / `remove_integration`：
  在基线上的独立集成副本按顺序试合并，冲突即停并报告；集成副本由工作台所有、
  可弃置，同样受脏区保护。文本可合并不代表接口兼容——试合并通过只是必要条件，
  真实集成验收仍要在合并副本上运行项目自己的检查。

**资源租约（`task_leases.py`）**

- 一份 JSON 注册表 + 控制器文件锁，每次变更在锁内重读重校验：两个派发方竞争
  同一资源时恰有一个获胜。
- 初版两类资源：`model:<model-id>`（每模型最多一项任务；别名/共享本地后端
  不算独立资源，由派发方在创建时保守判断）与 `integration:<名称>`；键的词汇表
  有意保持小，端口/浏览器 profile 等外部资源在后续批次扩展。
- 租约归唯一任务所有：释放他人占用被拒绝（取消/失败/恢复不能误释放其他任务）；
  所有者重复释放是幂等 no-op。
- **没有任何自动过期**：重启后由控制器按任务记录决定恢复；未知租约在人工决定
  前一直是占用。注册表损坏时全部操作拒绝（fail-closed），不自动重置。

**派发接线（DSH/Pi 编辑任务，串行保持）**

- 创建时：`workspace_plan_for` 只读计算隔离计划并随任务记录保存——Git 仓库根、
  HEAD 基线；声明的文件存在未提交改动（含未跟踪）时拒绝隔离并说明（基线会缺这些
  改动）；续接/整改以父任务成果提交为基线（`based_on` 记录来源分支）。非 Git、
  非 DSH/Pi、非编辑类任务不产生计划，行为与从前完全一致。
- 执行时：任务出队后由控制器创建 worktree（`prepare_workspace_for_run`）；
  崩溃残留分支报错拒绝复用。worker 内 `execution_roots` 把**记录身份与执行目录
  分离**：记录、会话、上下文索引、通知仍归属原项目（索引按原项目树缓存），
  文件校验、前后摘要、guard、cwd 全部落在 worktree。
- 完成后：控制器以固定工作台身份提交任务分支（`commit_task_results`），
  `.zcode`/`.model-desk` 控制器本地产物排除在外；执行器从不改 Git 历史。
  提交失败不改变已完成状态，worktree 保留待人工核对；失败/取消任务的脏
  worktree 原样保留。

**模型租约接线（每模型一项，串行保持）**

- 任务出队即 acquire `model:<model-id>`；凡执行模型的任务都持有（含 direct/aider
  与旧记录），使"每模型一项"在 `max_workers` 提升后依然成立。租约信息随任务
  记录保存。队列仍是单 worker，因此今天的冲突只可能来自陈旧注册表或不受管
  执行——两种都显式拒绝并说明持有者，绝不静默并行。
- 终态处理（完成/失败/取消，含控制器崩溃外的正常路径）在 `finally` 中由所有者
  幂等释放；外来释放始终被拒绝，取消/失败不能误释放其他任务的占用。
- 冲突接管在持有者任务记录锁内检查终态（completed/failed/cancelled），保持该锁
  直到租约锁内完成转移；仍在本控制器 MANAGED/ACTIVE 中收尾，或记录进程仍活跃/
  状态未知的持有者不能接管。接管记录 `recovered_from` 与原因。锁顺序为任务记录、
  ACTIVE_LOCK、租约注册表；不依赖锁外终态快照。
- 没有自动过期：面板重启后注册表原样保留，由上述接管路径或人工决定处理；
  注册表损坏时全部操作 fail-closed。

**受控集成验收（`task_integration.py`，控制器原语）**

- `run_integration(project, branches, name=, baseline=, checks=)`：在基线上的独立
  集成副本按序合并任务分支，然后**在合并副本上真实运行检查命令**并记录每个命令
  的参数向量、退出码、耗时与输出尾部——文本合并成功不代表接口兼容，结论只来自
  检查，不来自合并成功。
- 结论三种：`passed`（全部合并干净且每个检查退出 0，副本默认清理）、
  `merge_conflict`（合并序列停止、检查不运行、副本保留）、`check_failed`
  （检查全部运行、副本保留待查）。检查命令留下的构建产物同样阻止副本删除，
  记录如实标注 `kept_check_artifacts`，不做强制删除。
- 每项目同时只允许一个集成（集成租约），记录写入记录项目的
  `.model-desk/integrations/<name>.json`；记录是控制器工作流证据，支撑而非替代
  主脑对单项任务与集成结果的独立验收。
- 空 `checks` 被拒绝：仅试合并请用 `task_workspace.trial_sequence`；主脑驱动的
  调用入口（面板端点/主脑流程）在调度开放批次接线。

**批次等待语义（同模型冲突排队，不失败）**

- 模型租约冲突时分两种情况：持有者由**本控制器队列管理**（MANAGED/ACTIVE）→ 任务
  重新排队等待（保持 `queued`、阶段显示"等待模型占用（任务 X）"、`lease_wait`
  计数留痕），由退避定时器（30 秒）重入队重试；持有者**不受管**（外部执行、
  上一控制器残留）→ 拒绝并说明，等待只会空转。重入队前检查取消标记，取消
  即停止等待；等待期间没有发出任何模型调用，这不是重派。
- 完成监听器的批次语义无需改动：等待中的任务一直是 `queued`，批次仍一次
  订阅、全部结束后一次通知，异常状态照常显示为需处理。
- 重新出队的任务从头执行 `execute_task`：以最新设置重过作用域门禁（既有语义）、
  以冻结基线创建工作区（若首次尝试尚未到达该步骤）。
- 出队先在任务记录锁内原子领取 `queued -> running`，只有一个领取者可以启动；
  running、终态、待恢复任务不会因为重复队列回调而重跑。MANAGED 从领取起保留
  到成果提交及租约释放结束。过期等待回调重读状态，原尝试仍在收尾则继续等待。
- 租约冲突直接携带锁内观察到的持有者，不再二次读取可能已清空的租约快照；
  持有者恰好释放时仅重新尝试一次原子取租约，不重派模型请求。损坏注册表直接拒绝。

**限费预算与并行（审计结论 + `budget:paid` 租约）**

- 审计结论：账本的**每请求级门禁本来就是原子的**——`budget_relay.reserve` /
  `settle` 在 `budget.lock` 文件锁内完成"未结算阻断、任务/日上限、次数上限"
  判断并原子写账本与任务记录，跨进程有效；强制预算下同一时刻全局只允许一个
  在途计费请求，"单请求可越上限"是既有显式语义。并行不会破坏账本或造成超额。
- 真正的缺口在任务级：并行下第二个付费任务的首个请求会撞上"存在未结算费用"
  而直接失败，而不是排队等待。现以 `budget:paid` 租约补齐——强制金额上限开启
  时，付费任务持租约整个运行期，冲突走与模型租约相同的受管等待/拒绝/终态恢复
  路径；效果是强制预算下付费任务一次只跑一个（更保守但正确且简单）。
- 用户关闭上限（本安装的设置显式关闭）时不持任何租约、行为零变化；代码默认
  为 fail-safe 启用。未知费用的原生任务静态拒绝规则不变，本地模型不涉及。

**验收场景套件（`tests/test_parallel_acceptance.py`，已取消 skip）**

- 按计划的 7 个验收场景写就：真实两 worker 队列 + 可控假 worker（睡眠、向
  worktree 写交付物、发布终态），离线证明时间区间真实重叠、同模型排队、
  冲突阻止集成、预算租约串行化付费任务、取消隔离。
- 套件驱动的并发压出了**三个真实缺陷并已修复**：① 租约持有者在 Popen 前的
  准备窗口不在 ACTIVE 表，冲突方误判为"不受管执行"直接失败——新增 MANAGED
  集合（现为出队领取即登记、释放完毕才注销）；② 持有者记录定位只走租约内项目路径，定位
  索引陈旧时恢复永不触发——增加全局定位器回退；③ 无锁的并发 `git worktree add`
  争锁双双失败且失败清理可挂起——prepare/集成区创建改为每项目文件锁串行。
- 2026-10-25 复验确认原等待函数把仍在 queued 的任务当成“已收尾”，断言后
  Base.tearDown 先恢复注册表并删临时目录，executor 的 cleanup 尚未运行，造成
  线程继续读写消失的目录。已改为等待终态、控制器 Future 和退避 Timer 全部结束，
  在 Base.tearDown 前停止所有生产者；没有通过吞掉清理异常让测试变绿。
- 同步修正重复 checkout 已占用任务分支、错误的基线断言；并行重叠用屏障证明，
  不依赖 sleep 恰好赶上。强制预算测试用两个不同模型，排除同模型租约的干扰。
  增补未提交用户文件保留、真实合并冲突、检查退出码非零阻止集成通过的断言。
- 生产侧新增防护覆盖重复领取、终态仍在收尾、锁内恢复、进程状态未知不接管、
  释放瞬间的租约冲突、过期 Timer 不重跑。集成 `record=False` 不再被同名结果变量
  覆盖，不会意外创建项目记录。以上为临时项目、假执行器的离线检查，不是原生模型验收。
