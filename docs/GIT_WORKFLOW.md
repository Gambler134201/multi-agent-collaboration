## 每项改动的步骤

1. 确认当前分支、工作区改动和任务范围；保护用户已有修改。
2. 从合适且明确的已验收基线建立短期分支。示例：`chore/source-reconcile-dev`、`feat/brain-core`、`feat/brain-dsh`、`fix/completion-binding`。不要预先建一堆空分支。
3. 新功能优先在独立 worktree 目录开发，保持本机运行目录的文件不变。worktree 只隔离版本工作目录，不隔离端口、数据库、账户或外部服务。
4. 一次提交包含一个完整、可说明的变更及必要验证。写清解决什么问题，避免把多个无关任务堆在一起。
5. 提交前检查 `git diff`、待提交清单与相关测试；回归使用 mock 和临时记录。执行模型报告测试通过，仍需主脑独立检查。
6. 验收后查看分支与 `main` 的差异，再按授权范围推送/创建 PR/合并；涉及公开上传时检查全部新增历史，不只看最终文件。
7. 发布版打明确的版本标签；功能分支完成合并后再清理。合并前确认部署路径和配置，不能直接在运行目录切换未验收代码。

## 文件与权限边界

- 提交产品代码、必要测试、通用文档与依赖锁定文件。
- 不提交模型/账号配置、密钥、`.model-desk`、运行日志与会话、虚拟环境、依赖缓存、临时任务、截图、视频和导出包。
- `.gitignore` 对已经跟踪的文件不自动生效；初次整理和后续新增敏感路径时必须核对 Git 索引。
- 不自动提交/暂存/丢弃用户在其他任务中的改动，不强制推送，不以 `reset --hard`、`clean -fd` 或自动 stash 清场。
- 本机 Git 配置与身份沿用现有仓库；账号登录、运行配置、全局协作开关和预算设置不因版本整理改变。

## 开发目录使用

源码整合的 worktree 从公开 `main` 开始，使用 `chore/source-reconcile-dev` 分支；它与运行项目目录分开。先保留并验证已发布版本的安装能力，再把本机新增功能按可审查的改动迁移进去。整合完成前，多主脑运行逻辑仍属于后续任务。

worktree 没有本机模型配置、记录和虚拟环境是正常情况。可以显式使用现有 Python 解释器运行该目录里的离线测试，但不能把运行目录的 `.model-desk` 或模型密钥复制进去。新主脑与执行器的真实调用另按具体任务授权及现有工作流处理。
