## 1. 先关闭可靠性缺口

- 复现并修复场景测试提前结束、清理早于线程退出的问题，取消套件 skip。
- 原子领取任务，禁止重复入队/过期通知重跑；租约转移保持持有者记录锁，等待
  控制器成果提交和释放完成；损坏注册表与未知进程保持拒绝。
- 用屏障证明重叠，用不同模型验证预算串行，检查用户未提交文件保留及合并/
  集成检查失败。只跑派发、租约、工作区、恢复、阶段与通知相关增量回归。

## 2. 接入原生执行端的独立工作区

- 按 `PARALLEL_NATIVE_WIRING_CHECKLIST.md` 逐项拆分记录项目与执行根。
- WorkBuddy/ZCode 的 Python、Node guard、会话索引、版本与 job/proof 绑定必须
  同时更新；旧任务/旧保护版本不自动迁移，不牺牲记录隔离来绕过断言。
- 控制器配置及会话索引保持归属原项目；原生工具继续用产品自己的实现。
- 离线覆盖错误记录项目、伪造执行根、旧模式兼容及两个不同任务的交叉访问拒绝；
  真实原生闭环另外验证，不能用 mock 结果概括。

## 3. 开放有限调度与可验收的集成入口

- 先建立明确的批次准入与有限并发配置，默认串行；不能只改 max_workers。
- 共享物理模型服务、账户/会话通道与别名按资源冲突处理；未隔离任务需有项目
  串行屏障。端口、数据库、浏览器 profile 不会被 Git worktree 隔离。
- 只有已独立验收的前置任务才能解锁依赖。批次结束后在集成副本检查语义兼容，
  不自动覆盖用户工作树，不把执行 completed 或文本可合并当作 accepted。
- 完成通知要覆盖控制器成果提交/集成的收尾状态，避免主脑提前读取空交付；
  重启、取消、未知结果不重复调用，不误释放别的任务资源。

## 4. 再部署与验证宿主

- 满足上述门禁后，复查 Codex/DSH 公共入口与每个执行端。
- 冻结源码清单，核对导入依赖、运行差异和备份；空闲时再部署，不动正在运行
  的用户任务，不重启用户应用，不顺带调整预算/权限/模型。
- 单独记录源码、安装与真实任务证据。GitHub 发布另按用户授权处理。
