# 批准计划中的前置分支自动集成

2026-10-29开发，随后用户授权成组安装，9文件后台与DSH 0.2.19已部署并完成安装后协议/资源核对。用户确认DSH原生入口并批准真实计划；根任务一项failed、一项accepted，未触发集成及下游，整体尚未通过。见[部署与验收状态](APPROVED_FANIN_DEPLOYMENT_20261029.md)。下文保留实现范围。

## 本批解决的问题

原流程能并行完成两个独立阶段，但共同下游会停在“等待已验收集成基线”，需要主脑手动创建集成作业。本批把这一步接入批准计划，没有另建调度器、工具保护层或验收机制。

实施顺序：明确检查计划及批准摘要 → 接入原集成请求/队列 → 保留独立验收门槛 → 补异常及两主脑检查 → 审查提交。核心实现由Codex完成，无执行模型调用。

## 用户能看到什么

批准页增加“前置分支联合检查”：列出具有多个直接前置阶段的汇合点和检查命令参数数组。主脑可在 `brain_plan draft` 的 `checks` 中提出具体命令；也可在页面高级项编辑，然后更新预览、重新勾选确认。编辑未重新预览前不能批准或续接，检查变化会改变批准摘要。

检查不是从任务文案、测试文件名或历史命令中推测。`[]` 保持原行为：等待主脑手动集成。使用非空数组时，每项是直接执行的参数向量，例如 `[["python", "-B", "joint_check.py"]]`，不交给Shell拼接。命令在集成副本中运行，环境限制沿用已有集成执行能力；不是操作系统隔离承诺。

## 推进顺序

1. 每个前置阶段先完成真实任务、独立验收、收尾与有效文件哈希交接。
2. 若已有包含全部前置成果的基线，沿用原基线规则；不为一条串行依赖额外做合并。
3. 若至少两个前置成果需要合并，且用户批准了明确检查，计划先持久化原集成意图，再进入现有队列。记录绑定下游阶段、原任务、检查参数、原请求引用和确定的作业名称。
4. 队列冻结实际成果提交、持有现有项目集成锁，在独立副本合并并运行检查。检查通过只表示等待集成验收。
5. 原主脑通过现有集成验收入口记录独立证据。计划再次核对原作业及实际包含全部前置提交的已验收基线后，才允许下游入队。

不会自动验收、修改原项目树、合并main、部署或推送。没有下游汇合点的多个末尾独立分支，不在本批自动最终合并范围内。

## 异常和恢复

- 重复通知共用同一原意图；已运行、检查失败、冲突、取消或待恢复的作业不重建、不重跑。
- 入队回执丢失时，只读查找预先确定的名称；原作业不存在仍标未知，不据此重发。重新批准也保留旧意图。
- 原作业仍为queued时，可通过相同请求和现有队列重新附着；不换请求编号、不产生第二份作业。主脑作业仍需原受信责任会话，面板不能代派。
- 已保留集成意图后，不能因另一个基线出现而跳过原作业的未知/失败/待验收状态。任务、目标或检查不匹配须人工处理。
- 暂停、撤销或总开关关闭阻止后续新集成提交；已开始作业沿用原生命周期，不强行取消。
- 作业完成和集成独立验收唤起同一进程中已经附着的计划。服务重启不凭持久记录创建主脑授权；需原主脑明确续接。外部进程直接写集成验收的自动通知不在本批范围内。

## 接线和检查范围

公共实现位于 `approved_plan`、`integration_queue`、`brain_plan`，本地控制器与Codex/DSH正式主脑入口分别附着原队列回调。共用页面适用于Codex内联与DSH网页，不新增静态资源。正式工具schema支持draft/preview的checks，status可只读查看原集成意图。

验证使用临时SQLite/任务记录、本地Git副本、实际Python检查命令和模拟执行器，不连接账户、不派真实模型、不读取运行版任务或认证文件。真实临时Git用例验证：独立分支→联合检查→停在待验收→独立验收记录→下游取得合并提交，原树HEAD和文件保持。另覆盖回执丢失、并发通知、检查失败/冲突/取消/未知、权限开关、检查变更、错误归属与原queued附着。
