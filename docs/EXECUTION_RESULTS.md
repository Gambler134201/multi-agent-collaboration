# 执行结果与失败阶段

2026-10-23：首版源码已接入 Pi、DSH、WorkBuddy 控制器，以及工作台、Codex/DSH 正式读取和 CLI 交付包。部署和原生界面确认另记；不代表重新实跑三个真实模型。

## 展示和读取

任务详情增加紧凑的“执行结果”：原始执行状态、记录的阶段、首个具体失败、已有文件、指定自测和主脑独立验收。多个问题及阶段明细可展开。公共只读字段为 `execution_result`，带 `schema_version=1`；来自同一 `execution_result.project()`，不启动服务或模型，不修写历史记录。

阶段包括准备、执行、验证与自测、临时清理、会话关闭、成果核对、结果记录。阶段没有证据时显示未知；`not_run`、`not_requested` 和 `unknown` 分开。临时文件默认未知，不能因为正常结束或会话关闭就声称已经清理。

控制器只在实际操作边界写入 `execution_evidence`。工具发生在一个原生回合中时，不能仅根据文件生成或答复文字，推定模型内部已经完成了生成、测试和清理。WorkBuddy 已核实的固定拒绝规则 `unverified_recursive_cleanup` 可定位到临时清理；其他工具拒绝没有相应证据时仍属于执行阶段。通用的原生失败可由相关工具拒绝细化，但所有原始问题保留。

Pi/DSH 在指定自测和本任务子进程关闭后才发布执行终态；关闭未确认时保留成果并记失败，不先通知完成再改失败。WorkBuddy 沿用本任务原生会话关闭后记录终态的流程。新增摘要不改模型、权限、预算、任务范围、通知责任或恢复/整改策略。

## 证据含义

- “有文件改动”只代表记录时对任务声明文件的核对，不是全盘审计，不保证当前文件仍为该版本，也不代表成果通过验收。成果核对失败时不声称没有改动。
- 指定自测的退出码不等于主脑独立验收；WorkBuddy 的成功还需匹配命令和可信工具结束证据。未运行、未要求、证据缺失分别显示。
- `accepted` 与 `final_accepted` 仍取自权威验收记录及逐条证据检查；后者显示主脑接手后通过，保留执行器失败，不计执行器独立成功。任务内缓存的 `review_state` 不能作为验收事实。
- 固定控制器/工具规则码与历史错误文字推断分开。新阶段记录不因为“权限模块测试失败”等业务文案被归为系统故障；无法分类仍为未知。后续会话关闭问题不会覆盖更早的执行或测试问题。
- 本地记录写入与会话关闭问题分别显示，不能证明原生工具/提供方从未发生副作用。结果未知不授权自动重发。

旧任务读取时只生成只读投影，不迁移或补造阶段；已有测试退出码、WorkBuddy 会话关闭记录可保留来源，其余未知。原始 `status`、`error`、文件、验收和费用记录不因查询改变。

## 入口

- 工作台：任务详情，两主脑共用同一 JS/CSS。
- 通用主脑：`brain_status`、`brain_delivery` 返回相同 `execution_result`。
- Codex CLI：`workflow_assist.py packet` 的 `execution_result`；已有派发/等待路径不变。
- Codex MCP Apps 打包相同组件，普通 HTTP 页面也使用相同资源；已有页面需刷新，常驻进程按部署要求加载新源码。

该版本不包含离线 doctor、诊断包导出、自动回放或验收后制品变化提示；这些仍是后续独立更新。WorkBuddy 自动初始化按用户决定暂缓。
