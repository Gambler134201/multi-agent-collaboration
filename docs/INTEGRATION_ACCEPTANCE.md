## 两步职责

1. `brain_integrate(request_id, task_ids, checks)` 冻结当前项目、当前责任会话中已经独立接受且已收尾的任务提交，在隔离集成副本合并并运行检查。返回 `integration.name`、输入提交、输出提交、检查和保留副本。`verdict=passed` 不是独立验收，也不更新用户原树或 main。
2. 主脑检查实际合并成果并独立复跑后，调用 `brain_accept_integration(request_id, name, criteria)`。每条 criteria 必须为 pass，并有主脑独立证据。后端重新核对任务归属、验收绑定、冻结提交及集成副本；通过后记录 accepted_commit，可供既有阶段依赖选择集成基线。

两个操作使用不同 request_id；不得把第一步的请求引用当作第二步的身份。调用参数不接受自填 owner、project、actor 或会话：项目和责任绑定来自受信连接。未绑定的本地 CLI 历史任务不会自动收养到某个主脑会话；其原控制器工作流仍使用公共核心，不能伪造原生主脑工具全链路证据。

## 重复请求和响应丢失

相同验收请求与相同参数返回原验收回执，不重新合并、测试、派发或执行验收。相同请求改证据或名称拒绝。丢失响应后用 `brain_request_status` 核对原 request_id；新验收原子记录其 acceptance_request_reference，只有归属于该请求的结果才能确认成功。其他请求或旧内部 Python 验收不充当本次成功证据。

未能确认的请求保持 unknown，不以新 ID 重试；`safe_to_redispatch=false` 保持。新入口不增加自动重试或自动推进。

## 公共核心约束

`task_integration.accept_integration` 复用现有项目 integration 租约，所有调用方同样串行；每次调用使用独立持有者身份，不能把同名集成误当成同一持有者而绕过互斥。与其他集成或验收冲突时拒绝，不释放其他调用的占用。未接受、未收尾、过期提交、脏副本、缺副本、非独立证据均沿用既有拒绝。

客户端对 integrate、accept_integration、finalize 分别校验成功响应结构。成功回执不会再落入只适用于 describe 的 context 兜底，损坏结构仍保留 unknown；不能通过取消结构校验来掩盖协议缺口。

进一步核对回执中的 request_id，以及验收 name/收尾 task_id 是否匹配原请求；已接受却检查失败的矛盾验收结果不能作为成功。HTTP 正文即使能解析为 JSON，只要声明的 Content-Length 未接收完整也视为响应丢失；分块传输等 HTTP 协议错误同样保留 unknown，并带原操作和请求引用，不自动重试。

## 已验证与限制

## 部署前检查边界

部署计划应核对六个配套 Python 模块（brain_context、brain_requests、brain_gateway、brain_mcp_server、brain_transport、task_integration）和 DSH 工具白名单，不单独替换客户端或后台一侧。先按实际已安装文件生成哈希备份；DSH 包版本、清单和收据按实际安装状态重建，不拿旧收据强行覆盖加载中的插件。原生任务结束、旧 MCP 连接卸载后再切换，随后使用新连接核对两个宿主的工具列表与独立验收链路。

只生成差异/兼容/回滚检查单不等于部署授权；模型配置、账户数据、设置、运行记录、并发调度器与自动集成队列均不在本候选替换范围。失败时按本包准确原文件恢复，不回滚用户任务或账户设置，也不以重启桌面作为通用恢复手段。
