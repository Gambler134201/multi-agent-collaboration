## 用户流程

已有明确项目、目标和阶段后，在进行中目标点击“批准计划 / 推进状态”。预览展示每阶段目标、依赖、固定模型/执行端、访问模式和验收条件；用户勾选边界后可批准并启动。没有明确模型的阶段先要求固定一个模型或只保留一个候选，不由控制器重新规划或偷偷替换。

责任主脑草案另展示不可变owner/会话声明。用户批准后，由这个原会话明确调用 `brain_plan(action=resume)` 附着；普通工作台不代它派发。批准文档绑定责任模式，主脑不能自行批准、解除暂停或接管其他聊天；本地控制器计划仍沿用原工作台推进入口。

批准后普通无前置阶段通过原 `dispatch_stage` / `submit_task` 入队；是否实际并行由原调度与共享资源决定。执行器完成只进入待独立验收；主脑通过原验收和成果交接入口完成审核后，同一服务进程收到事件再检查下游。必须有有效交接，多个独立前置分支还必须有已独立验收的集成基线。首批等待现有集成入口处理这些分支，不猜测、生成或自动执行联合检查命令。

暂停/撤销阻止后续新领取，不取消已排队或运行任务；这些任务继续按原取消/收尾机制处理。目标取消也不复活。全部阶段经过真实验收记录同步后，计划可显示“阶段全部验收通过”；不自动更新用户工作树、部署、推送或合并 main。

## 持久化与身份

- 复用项目 `.model-desk/records.db` 的 `goals.data.approved_plan`、阶段与 `stage_log`；不新增数据库、任务状态权威或调度器。新增的是主脑计划协作入口，不是执行器的文件/终端工具。普通列表只返回紧凑摘要，查看计划才返回完整批准内容。
- 内容摘要绑定项目、目标/阶段定义、依赖、会话策略、固定模型/实际执行端、访问模式、有限模型配置摘要、执行端预设/选择摘要、预算/范围策略及根Git基线。自动编辑首版需要已有Git基线，不替用户初始化Git；只读阶段可用于非Git项目。
- 改目标/阶段、模型选择/参数、有效执行端、权限或基线导致摘要不符时，停止并要求重新预览批准。总开关和执行端开关仍由原派发门禁决定，批准本身不扩大权限、不关闭计量限制。
- 重新批准保存旧批准版本的内容与摘要；每次派发意图注明其原批准版本。新版本不能把旧未知意图改绑到新版本后重发，普通目标列表不重复传送这些完整历史。
- 不持久化密钥或账户认证；摘要不是抵御任意本机写入的签名。`confirm=true` 是调用者的明确授权声明，不是可信原生“用户确实点击”证明；使用该接口的主脑必须取得真实用户授权，不能自行批准任务。
- 首批本地控制器归属保持；第二批只有已批准且责任匹配的 `brain_plan` 能进入签名阶段派发。普通 `brain_dispatch` 仍不能任意覆盖阶段/目标；原子领取同时核对责任主脑、原意图、当前内容、实际模型/执行端及控制器签名。不会伪造owner、借面板绕过签名或自动收养其他聊天。

## 防重复和故障

每个阶段先在原项目DB落盘一次派发意图，再调用原派发入口；实际阶段领取仍在原SQLite事务内，追加核对批准版本、原意图、实际模型/执行端和当前定义/权限。一个意图不允许领取第二个任务。批准、暂停、撤销和推进按单个目标串行；暂停返回后不再有该计划的新领取，已领取任务不受影响。

- 派发中丢失回执或出现不确定异常，保留原意图和原阶段任务，不自动改ID重发；新版本批准也保留未知意图。
- 共享控制器能正面核实阶段的原子领取完全未发生时，记为 `not_submitted`。它与结果未知不同；用户检查后明确续接/重新批准才允许再次尝试，旧意图留在历史中。一次普通通知不会自动重试。
- 执行失败、退回、取消、保护拒绝或待恢复分支需要主脑处理；首批不自动发整改任务，已有一次整改限制及原生Agent纠正常规工具错误的行为保持。
- 重复事件合并到现有 `ThreadPoolExecutor` 的有界推进检查，无额外模型循环。读取/打开页面/导入模块不启动任务或服务。
- 重启不自动附着或重发，保留批准版本，需显式续接。附着关系只在进程内，未持久保存或伪造主脑签名授权。

## 第二批正式主脑动作与原请求

`brain_plan` 固定动作：

- `draft`：先校验固定模型、1–20阶段及无环依赖，再保存尚未获批准的草案。部分写入草案标记未完成，不能批准或用prepare补造完成。
- `prepare`：为尚无原任务、无推进历史的工作台草案绑定当前责任主脑；不覆盖其他主脑或接管已执行计划。
- `status` / `preview`：只读；普通status不重复全文批准历史、不暴露内部意图token，明确预览才返回原文。
- `resume`：仅原责任会话按原摘要附着有效批准；用户暂停必须先由工作台解除，权限/模型/基线漂移须重批。
- `handover`：仅为本责任已收尾、已独立验收的原任务生成真实文件哈希交接。提前请求在落盘前明确拒绝；实际保存后丢回执由原请求引用核对，不以回答自报替代。

四种变更均走既有请求账本；计划步骤派发另有先落盘的稳定request_id，状态可直接取到原请求编号。`brain_request_status` 可返回 `plan_found` 及原事实，始终只读、`safe_to_redispatch=false`；丢回执不重建草案或发第二任务。责任签名仅在当前后台内存，不持久存储或伪造；本机已按用户授权部署DSH 0.2.18及配套代码，常驻连接与原生业务验收仍分开记录。
