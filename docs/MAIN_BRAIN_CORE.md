## 本轮范围

共用现有路由、派发、项目记录与独立验收机制，新增独立 stdio MCP 入口。提供连接/身份说明、候选模型查询、预览、快速派发、状态、交付取回和验收/退回整改。保留原 Codex 面板 MCP、CLI 和完成监听；不替换当前部署。

本轮不开发多模型并行、跨主脑接管、聊天同步、额度自动切换、跨项目自动唤醒或新宿主原生 UI。DSH 主脑基础闭环属于下一阶段，不能由 mock 工具闭环推定。

## 身份和权限决定

- 启动入口由用户/宿主配置绑定绝对项目路径、宿主标识、主脑职责和会话责任归属。工具参数不能改项目、宿主、角色或拥有者；不从服务安装目录、cwd 或全局最近项目推断它们。
- 原生会话 ID、宿主版本、模型身份要区分已核实、启动时声明与未知。缺少宿主原生会话来源时，可由用户在启动配置中明确绑定一个专用会话标识，记录为显式用户绑定，不伪称从宿主核实；缺少这两类归属时，变更工具拒绝执行。
- MCP 连接通过受信控制器建立私有会话能力令牌，留在传输进程内部，不进入工具结果、模型参数、任务提示或执行器环境。服务端以该能力查找不可变连接上下文，不能信任每次请求中的 actor/owner/project 字段。注册入口沿用当前本机控制器授权边界，不向模型开放。
- 新任务在排队前记录真实主脑拥有者和请求标识。结果读取与验收检查项目和原拥有者；旧任务不自动补身份或被新主脑收养。新主脑任务的验收/整改不能由旧 CLI 或普通 HTTP 请求仅靠填写 actor 获得权限。
- 主脑接口只暴露明确的协作操作，不提供任意 HTTP 路由、命令执行、配置写入、令牌读取或任意文件读取；执行器不挂载此主脑 MCP。已有本机管理员和任意同用户脚本的权限不属于 OS 沙箱，本项目只承诺工具/控制器边界，不能声称阻挡恶意同用户进程。

## 派发与结果决定

- 每次变更请求使用调用方明确给出的 request_id；服务端按项目、主脑拥有者、request_id 和规范请求摘要去重。同 ID 同内容返回原结果/原任务，同 ID 不同内容拒绝；并发提交不能排队两次。
- 在项目自有控制器记录中先保留请求，再执行变更。响应丢失或进程崩溃后的结果未知，不自动再派；能够从原记录确认结果时只取回原任务。不得把失败/缺件/解析错误改成成功，也不得通过换请求 ID 自动重试。
- 派发快速返回任务 ID；状态与交付读取不等待模型、不重复派发，不把工具超时当作任务总时限。总时限默认仍为零。
- 路由继续使用本次显式覆盖 > 每模型默认 Agent > 全局回退；范围、付费、可选预算/次数限制、旧会话锁定、交接、独立验收和一次整改限制继续由原核心判断。
- 取回结果时区分执行状态、主脑验收、执行器自报和独立证据；不能生成并不存在的检查证据。独立验收依然要求逐条证据。

## 阶段 A 实施状态（2026-10-18）

状态：**通用核心/工具 mock 闭环已实现，经主脑接手修正并完成独立验收；仍未接入任何新增原生宿主。宿主实际入口、规则加载与原聊天能力的核对尚未完成，不把本轮记为全部宿主调查完成。**

已实现：

- `brain_context.py`：受信启动上下文；显式绝对项目绑定；角色、不可变拥有者、声明/核实/未知身份与会话责任归属分离；缺少责任归属拒绝变更；控制器侧签发并校验签名授权。
- `brain_gateway.py`：面板侧固定操作 broker；控制器授权的私有连接能力注册；按能力查不可变上下文；按项目+宿主+原拥有者+责任会话解析任务；拒绝旧任务/其他拥有者/其他项目/其他聊天；复用路由、`submit_task`、验收与整改核心。
- `brain_requests.py`：项目自有 `records.db` 请求日志；规范 payload 指纹与持久化幂等；先保留后执行；同 ID 同内容返回原回执、不同内容拒绝；并发只允许一个效果；重启/响应丢失/异常后不重放，只恢复真实可归属记录或返回原请求引用。
- `brain_transport.py`：有界回环 HTTP 客户端；无代理、无重定向、变更无自动重试；能力只保存在进程内；初始化/工具发现不联网；显式连接要求服务已运行；后端重启后要求显式重连。
- `brain_mcp_server.py`：独立 stdio MCP 入口；固定九个工具（连接、说明、候选、按模型预览、快速派发、状态、交付、验收/退回、整改）；严格 schema 与运行时未知字段检查；不含任意 HTTP/命令/文件/配置/授权工具。
- `panel_server.py`：私有 broker 路由；受信上下文内部传入任务创建；入队前持久化公开拥有者/请求元数据；来源如实记为 `brain`；主脑任务初始化成果委派；续接/整改/任务链接拒绝跨拥有者、跨项目和旧任务收养。
- `delegation_policy.py`：主脑任务的 `init/accept/final_accept/return/block`、整改认领/释放需要经控制器验证且拥有者/项目匹配的授权；普通 `actor='main'`、旧 CLI 与普通面板路由不能验收主脑任务；执行器上报仍允许且永远不能验收；旧非主脑任务行为不变。
- `project_storage.py`：项目 `records.db` 新增 `brain_requests` 表，主键 `(owner, request_id)`；这里的 owner 列保存完整责任绑定的摘要（含项目、宿主、角色、拥有者和会话），同一人不同聊天不会串用回执。

工具固定为：`brain_connect`、`brain_describe`、`brain_candidates`、`brain_route_preview`、`brain_dispatch`、`brain_status`、`brain_delivery`、`brain_review`、`brain_rework`。派发快速返回原任务 ID；状态/交付/验收读取不等待模型、不重复派发；整改保持原模型/执行器并使用新会话，仍受一次整改限制。

## 本机接入步骤（可移植，不提交运行配置）

1. 先显式启动工作台（不会由主脑 MCP 自动启动）：

```powershell
.\打开模型工作台.ps1 -NoBrowser
```

2. 由宿主/本机配置启动独立入口，项目路径使用你自己的绝对目录；以下只是示例占位：

```powershell
.\.local-worker\venv\Scripts\python.exe .\.local-worker\brain_mcp_server.py `
  --project "D:\dev\my-project" `
  --host dsh `
  --owner main-a `
  --role brain `
  --session-binding user_bound `
  --session-id "main-a-user-session-1" `
  --panel-url http://127.0.0.1:8765
```

`--session-binding user_bound` 是显式用户绑定的专用会话标识，不是从宿主原生会话核实；阶段 A 不接受 `host_verified`。没有 `--session-id` 时保持 `unknown`，变更工具会被拒绝。`--host-version`/`--model` 只记为声明，不伪称已核实。

3. 宿主首次调用 `brain_connect` 显式连接；服务未运行会返回明确不可用错误，本入口不会启动服务。
4. 工作台重启后旧能力失效，需要重新调用 `brain_connect`。
5. 该入口不注册到 DSH/Pi 执行器，也不由 `setup.ps1` 默认注册到 Codex；宿主侧配置需要用户显式添加。

重点覆盖：

- 真实 JSON-RPC stdio MCP `initialize`/`tools/list` 握手；初始化与工具发现零 HTTP 请求；显式连接后才联网。
- 临时项目 + 临时注册表 + 临时回环 HTTP 面板的真实链路：连接 → 候选 → 按模型预览 → 异步派发 → 运行中状态 → 执行器完成但未验收交付 → 缺陷退回 → 一次整改（同模型/执行器/新会话）→ 独立逐条证据验收。
- 并发重复派发只执行一次；同 ID 不同 payload 拒绝；响应丢失、重启和效果后异常不重放；重复验收/整改不额外消耗次数。
- 普通面板路由/CLI 不能验收主脑任务；执行器角色、错误拥有者、错误项目、旧任务收养均被拒绝。
- 临时任务记录与请求日志中不出现控制器能力/面板令牌/模型密钥。

主脑独立结果：

- 新接口六个测试模块共 56 项已验证：先运行 55 项全部通过，补充本地模型默认 Pi 的场景后，网关模块 16 项全部通过；身份/归属最终调整后两个模块另跑 18 项通过。
- 完整回归运行 1015 项，200.824 秒，仍有两项既有 DSH 环境依赖错误、11 项跳过，没有新增失败；新增 Pi 用例在此后定向验证，不倒写为完整回归已经包含它。两项错误仍是缺少 DSH 运行依赖导致的续接拒绝、未配置 DSH app.asar 路径。
- 主脑先补出可复现的跨会话读取、跨聊天请求 ID 串用、写入后异常误报、坏响应和凭据反射场景，再修正；同时保护总开关关闭时不派发新任务、原请求仍能取回。
- 验收写入后出现异常时，只有真实记录带有同一请求标识才恢复原结果；否则保留未知。不会把写入后的异常一律当作未生效。
- 本机运行目录源码和公开 main 保持原状，测试只用临时记录、模拟提供方与模拟宿主；回归无真实模型调用或真实聊天通知。执行任务本身经工作台调用了授权的执行模型，因接口故障中断，随后由主脑接手；保留原执行失败，不改成执行模型完成。

## 新主脑宿主接入的固定检查顺序

上述阶段 A 是历史基线；DSH 后续原生验证及当前范围见 [DSH 主脑插件记录](DSH_BRAIN_PLUGIN.md)。后续宿主复用通用网关、路由、任务账、验收与执行器保护，不重新实现这些规则。宿主适配分别核对以下项目，缺少能力时明确标记，不通过改通用权限来补齐：

1. 项目/聊天：未知项目不猜测、空项目不初始化记录，原生会话切换和旧连接回收分别检查。
2. 插件生命周期：先启动互不依赖的功能；Agent/MCP 绑定阻塞不拖住账户采集。用产品自带框架验证服务解析、属性访问、延迟加载与卸载。
3. 模型真正可见的工具结果：使用安装版客户端完成解析和文本渲染检查；协议存在 structuredContent 不等于模型能读到字段。核对成功、错误、候选范围和交付长度标记。
4. 账户与页面：主脑宿主余额和执行模型 API 余额分开，模拟快照不能作为真实账户接通证据；原生入口与显示仍需人工确认。
5. 执行闭环：同项目完成一次任务和一次真实缺陷整改，核对模型/Agent 路由、独立验收、范围负例及共享记录保护；执行器 completed 不能替代 accepted。
6. 等待/唤醒：单独验证宿主是否支持后台等待与一次完成通知。没有实测就标记未支持，不根据 MCP 接通推断自动唤醒。

前三类兼容问题尽量在候选阶段以真实框架和模拟接口复现；完成这些检查后再安排一次原生安装与人工验收。共享保护回归见 tests/test_record_protection.cjs、test_record_protection_runtime.cjs 和 test_pi_runtime.py；它们属于执行器层，不要求每次重装主脑插件。当前不把这份清单称为自动适配器或全自动认证。
