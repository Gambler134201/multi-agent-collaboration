# Completion-driven local desktop waiting

Completion-driven wakeup must first be verified for the current local desktop and chat. A source distribution does not inherit any other installation's diagnostic results. Cloud/other-host compatibility, restart-proof delivery and exactly-once transport after an ambiguous response are not promised. No recurring GPT heartbeat is used.

The shared completion core selects a bound host adapter; an unavailable/unknown host never falls back to another chat. Codex retains its existing verified local path. DSH 0.2.5 is probe-only; 0.2.6 adds the formal `brain_wait` task tool after the user confirmed the native probe returned automatically. For DSH: connect, finish dispatching the batch, call `brain_wait(action=start, task_ids=[original ids])` once, announce waiting only on `waiting=true`, then end the turn. On the fixed event call `brain_wait(action=received, wait_id=original id)` and independently review via the existing scoped delivery/review tools. status/stop use the original wait id; stop does not cancel workers. No automatic resume, retry or repeated model polling; a dead/stale listener is unconfirmed. The new tool requires original owner/binding even when project history is readable. A new rework task needs its own subscription. The CLI instructions below are for the existing Codex path, not an ordinary DSH shell: only the bound native MCP gets the private DSH channel. One native DSH single-task completion/receipt/review loop has passed human observation and independent record/file checks; native bulk/fault paths remain separate, and probe success alone never proves them. Closing/disabling/restarting DSH can stop notifications without cancelling execution.

`brain_wakeup_probe` remains an explicitly requested diagnostic: start, confirm waiting, end the turn and acknowledge the fixed event with received. Use the original probe id for status/stop. It waits about 30 seconds and for the original Agent to become idle, attempts once, and has process-local state. Ask the user not to message/close DSH during this diagnostic and offer a 90-second observation window. Normal task waiting remains interruptible. Event delivery invokes a main-model turn; local waiting does not invoke the model.

For one new task use `dispatch_task.py ... --project <trusted-calling-project> --notify-on-completion` from that directory. It preflights the current desktop chat/project before submission, submits once, starts a hidden local listener and returns a waiting receipt. Only a confirmed `waiting=true` authorizes saying “正在等待执行模型完成，结束后我会自动回来验收” and ending the turn. No periodic GPT polling afterwards. Task runtime stays unlimited. If startup fails after submission, report the original task id and attach to it; never dispatch again.

For a batch, submit its tasks without `--wait` or `--notify-on-completion`, then run `completion_wait.py --project <trusted-calling-project> --tasks <id1> <id2> ...` once after all ids are known. Check listener_status= listening/waiting_chat_idle. Do not enroll those tasks individually or in overlapping batches. Each task has one original notification owner. All tasks must belong to this project's own runs; the index, service cwd and another tab are not identity sources.

The local listener reads actual queued/running/terminal task records; silence or answer text never means done. It waits for the entire batch, then sends one fixed reference to the original chat when idle. Failed/cancelled batches and recovery_pending produce an attention event, never acceptance or automatic execution retry. During normal waiting the panel shows a persistent status; stale listener heartbeat is unknown, not task failure/completion. Interrupted/missing records and notification failures do not cancel workers. Importing these helpers does nothing.

On the completion message: first run the usual workflow switch check, tell the user “执行已结束，正在独立验收” or describe the actual attention condition, and acknowledge the matching reference using `completion_wait.py --project <project> --received <wait-id>`. Read one compact `workflow_assist.py packet --task <id> --project <project>` per completed task, inspect real changes and independently verify every criterion. Use review_task.py as before. Receipt is not acceptance; accepted/final_accepted comes only from the actual review. State “任务已完成，验收通过” only then. A single permitted corrective round gets a fresh task/session/subscription and an explicit “正在整改，继续等待” notice; existing stage/handover gates remain authoritative.

`completion_wait.py --project <project> --status <wait-id>` reads current local evidence. `--stop <wait-id>` pauses notification only. `--resume <wait-id>` is explicit and only for a proven-dead original listener before any delivery attempt, on the same reviewed source and original chat; it never dispatches a worker. Never remove send.claim or silently retry an unknown/rejected/attempted delivery. A stopped listener never cancels execution. Ordinary users can ask progress or change requirements; if they explicitly cancel the work, stop its notification and use the existing deliberate task-cancel path. Do not reuse this for messages to other chats.

For idle-wakeup diagnostics, explicitly say when waiting starts, temporarily ask the user not to message or close the app, give an observation window and tell them when they may ask again. Ordinary task execution remains interruptible. In all cases distinguish waiting, execution-ended/reviewing, accepted/completed, rework and attention; do not claim listening until startup is confirmed.

# Concentrated local waiting fallback

After dispatch, concentrate waiting in the local waiter: `--wait` is quiet by default; use `--progress` only for requested progress or a concrete diagnostic need. While queued/running, do not repeatedly read task records/logs, inspect source, duplicate the worker's investigation, or re-plan merely to check progress. Resume the same tool session/cell with the longest supported bounded wait up to 60 seconds; where supported, batch tool-only waits and output filtering inside one tool script. Silence is not a task failure or a reason to cancel, redispatch, or impose a deadline. If the waiter disconnects, use `dispatch_task.py --wait-task <original-id>`; this attaches without dispatching. Read the compact final result and perform independent acceptance after completion; handle actual errors or user decisions when they occur. This reduces controller activity, not a guarantee of zero host/model usage or an event-only native wakeup.
