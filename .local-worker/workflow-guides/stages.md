# Persistent stages and verified handovers

Persistent goals and stages are managed by `@ROOT@\.local-worker\stage_store.py` in each explicit project's `.model-desk/records.db`; task content is authoritative in `.model-desk/runs/<id>/task.json`, with logs/reviews/handovers alongside it. The global project index is only a locator; old global records remain migration backups and the fee ledger stays global. Create a goal and stages with `stage_store.py --create-goal ...` and `stage_store.py --add-stage ...` giving each stage a clear objective, dependencies, project/file scope, decidable acceptance conditions, candidate/fixed models and a `kind` (`chat` read-only / `edit` full access; migrated legacy rows default to `edit`). Dispatch a stage with `dispatch_task.py --stage <stage> --task-file <UTF8-task> [--request-output-tokens N]`; this uses the same queue, routing, authorization and switch. The optional request output target is task-level and does not change a model's max_output preset, and an explicit SDK max_tokens is still bounded by it. A dispatch cannot widen or override the stage's stored kind, acceptance conditions or candidates. A dependent stage may only be dispatched after every prerequisite stage passed independent acceptance. The scheduler only reports readiness and reconciles state with real task records; the main brain still plans and accepts. A dependent dispatch also carries its validated, hash-checked prerequisite handovers in the fresh prompt, and a missing or stale required handover blocks the new dispatch instead of silently sending an under-contextualized request. Every stage starts a new session in the selected execution Agent (DSH or Pi) by default; an explicit --engine overrides the saved default for that dispatch, and reuse cannot cross Agent identity. After a panel restart an unfinished dispatch is shown as 待恢复 (recovery_pending) and is never re-sent automatically; inspect it and use `stage_store.py --requeue --stage <id> --reason <...>` to allow a new dispatch. Cancellations are recorded (`stage_store.py --cancel` or the task cancel API); a cancelled goal or stage stays cancelled through sync/recover, readiness also blocks cancelled/completed goals, and a goal can only be marked completed when it has at least one stage and every stage passed independent acceptance.

Persist a stage deliverable as a handover with `@ROOT@\.local-worker\task_handover.py --create --task <id> --evidence-file <UTF8-JSON>`; the file digests are computed from the real files and a caller-written summary is stored as a claim, never as verification evidence. A handover can only be created after the task passed independent acceptance, and a reference must stay inside the same project/goal and a real prerequisite stage. Identity is read from the real task/handover records, so a caller cannot relabel, omit or spoof the stage/goal to reach another goal's deliverable, and a stale reference is refused rather than returned. Re-run `task_handover.py --verify --task <id>` and treat a stale result (changed or missing file) as invalid instead of trusting the old summary.

Supported API entries: `/api/goals`, `/api/stages`, `/api/stages/<id>/(dispatch|cancel|requeue|sync)`, `/api/recovery`, `/api/tasks/<id>/handover`, `/api/tasks/<id>/reference`, and model_desk `panel_request` with concrete whitelisted paths only.
