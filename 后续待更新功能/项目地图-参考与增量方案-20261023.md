# 项目地图：参考项目与增量方案

日期：2026-10-23。状态：讨论草案，尚未开发地图功能或安装第三方项目。用户表示对项目地图感兴趣，但尚未确定具体形态；本文件用于解释可选方向，不构成实施结论。

## 1. 参考项目真的有“地图”吗

有，但含义不相同，不能把文本代码索引、交互图谱和任务看板混为一项。

| 公开项目 | 官方资料中实际描述的功能 | 与我们讨论的关系 |
| --- | --- | --- |
| [Aider Repository Map](https://aider.chat/docs/repomap.html) | 用文件及关键符号/签名构建精简仓库上下文，并按相关性和 token 预算选择部分内容 | 主要给模型读，参考如何少读文件、选对上下文；不是可点击地图界面的同义词 |
| [GitNexus](https://github.com/abhigyanpatwari/GitNexus) | README 描述代码知识图谱、依赖/调用关系、交互 Web UI 及 MCP 查询 | 适合参考“人看关系图，Agent 查结构”的产品形态；本轮只核对资料，未实测准确性 |
| [CodeGraphContext](https://github.com/CodeGraphContext/CodeGraphContext) | README 描述将本地代码结构索引成图，并提供 CLI/MCP 分析与查询 | 参考图谱查询与影响分析；是否引入图库等依赖要单独评估 |
| 之前调研的 Raven、Agent Orchestrator 等 | 本次已核实的是编排、任务工作区、轨迹或状态能力 | 没有据此证明它们都实现了上述完整代码地图；不能把我们的设想反写成它们现成的功能 |

来源为上述官方文档与仓库 README，不引用第三方排名或效果宣传。GitNexus README 当前标注 PolyForm Noncommercial；这里只参考公开介绍，不直接纳入代码或依赖，后续若考虑集成需单独核对适用条款。未运行其 analyze/setup 等会修改项目或 Agent 配置的命令。

## 2. 我们已经有什么

已有 `.local-worker/context_manager.py`：

- 构建项目文件清单，任务范围内提取符号与签名。Python 使用 AST；部分语言使用模式提取，不支持时明确退化为文件级记录。
- 内容哈希、索引版本、范围匹配与新鲜度检查；已有索引引用进入执行提示词的能力。
- 默认排除敏感文件、运行记录、依赖与缓存；只为范围内文件提取细节，不代表已理解全仓库所有函数。
- 已找到 Pi、DSH 的接入调用；未找到 WorkBuddy 的同等调用，不能称其已经共用此索引。

另有 `panel_server.tree_view` 的“目标 → 阶段 → 任务 → 子代理”数据和现有任务树界面。它展示协作记录，不是代码依赖图。

因此，新增地图的工作是补“关系、查询、展示和上下文选择”，不是重新实现文件索引、任务记录或独立验收。

## 3. 建议的用户体验

地图应针对用户当前明确选择的项目，不只服务框架自身。打开另一项目时，只显示该项目的索引和合法可读记录。

第一层是模块概览：入口、核心逻辑、适配器、界面和测试。选择一个模块后展示：

1. 实际文件和关键符号，可跳到对应源码。
2. 静态可识别的导入/引用关系，以及解析方法与证据位置。
3. 相关测试和关联任务；测试关联需标注来源是显式配置、源码引用还是建议，不能把文件名相似当成完整覆盖。
4. 最新相关验收及其对应制品版本。历史 accepted 不等于当前代码仍通过。
5. 本次变更可能关联的上下文文件，供主脑审阅后用于派发。

例如用户要“新增一个执行端”，地图可将执行端设置、路由、派发、Worker 和相关回归入口集中显示，帮助主脑发现联动点。这个例子是设计目标，不是已由工具自动生成的真实调用链。

第二层再把任务叠加到模块：谁在处理、哪些文件有运行中任务、前置验收是否满足。协作状态来自控制器事实，地图不自行派发或宣布验收通过。

## 4. 实际价值与边界

对人：更容易看懂项目、定位改动范围和找到验证入口。对主脑：先查地图，再读必要原文件；对执行端：收到任务相关的精简上下文。这样有望减少重复探索，但需测量，不能提前承诺节省多少 token 或提升多少质量。

地图是导航与证据索引，不是运行时真相：动态导入、反射、跨语言协议、HTTP、MCP、插件和外部资源不一定能从语法树完整识别。区分“解析确认”“显式登记”“推测关联”“未解析”，不要画一条实线就宣称准确依赖。

模块职责的自然语言摘要可以先由人工确认；后续若用模型生成，需单独记录来源、成本与版本，不能为了打开地图自动调用付费模型。

## 5. 最小版本建议

| 步骤 | 做什么 | 验收重点 |
| --- | --- | --- |
| 1 | 复用现有索引，加只读模块概览与符号查询 | 不重复扫描依赖/记录目录，项目不明时保持未选择；无需模型调用 |
| 2 | 先补 Python import 及可静态确认的关系，之后再扩 JS/TS | 别名、相对导入、重名、动态引用明确处理；不支持标未知，不把导入图冒充完整调用图 |
| 3 | 工作台加入地图入口，先默认模块级，按需展开 | 避免满屏函数节点；节点能回到源文件，显示来源和索引是否过期 |
| 4 | 读取相关测试/任务/验收，叠加状态 | 不越项目/owner 权限，不因图上相连扩大读取范围；缺证据不显示通过 |
| 5 | 主脑按任务查询地图并选择上下文；逐端接入 | Codex/DSH 共用查询契约；Pi/DSH/WorkBuddy 分别核对实际消费索引，不把握手当生效 |

首版不需要向量库、全仓库语义总结或自动路由重写。也不直接在用户项目执行第三方“一键索引/安装”命令；先用临时样例验证文件数量上限、解析降级、内容更新后的失效与大项目性能。

模块地图可以独立于并行先做。它能提示依赖和资源关联，但不能取代并行调度的资源锁、worktree 隔离与集成验收。
