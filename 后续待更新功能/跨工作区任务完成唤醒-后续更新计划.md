# 跨工作区任务完成后唤醒原聊天

整理日期：2026-10-18。状态：已列入待办，尚未实现。先继续当前 DSH 主脑插件基础适配，再结合宿主通知适配实现本功能。

## 要解决的问题

当前聊天在运行目录，执行任务在独立 Git worktree 时，现有完成通知的同项目校验不能直接复用。本轮开发因此采用安静的同步等待；不能把它称为“主脑退出轮次，任务结束后自动回来”。

目标是：用户留在原聊天，执行模型在已明确归属的独立工作区干活。派发后主脑结束当前轮次，后台监听实际任务终态；同一批次结束后，正常情况下只唤醒原聊天一次，由主脑在**执行工作区**独立检查实际成果。

## 实现步骤

1. **分别保存两端身份。** 记录原聊天宿主/主机、原项目绝对目录及聊天 ID，同时记录执行工作区绝对目录、任务/批次 ID 和明确的委派关系。两端都来自受信宿主或用户明确绑定，不能从服务目录、最近项目、回答文本或全局索引猜测。
2. **保留原任务记录归属。** 任务、日志、交付和验收仍在执行工作区自己的 `.model-desk`，不复制一份到原项目伪装同项目任务。跨工作区关联只是通知和责任关系，不赋予任意项目读取/接管权限。
3. **增加显式跨工作区订阅。** 由控制器核验原聊天与所委派任务的关联，再给后台监听器限定的读取/通知能力。不要直接关闭现有同项目校验。未知、失效、无关项目和未授权任务仍拒绝。
4. **后台等真实终态。** 监听已提交原任务/批次，执行静默不算失败，执行器 completed 不算独立验收通过。主脑不周期性醒来查状态；不重复派发、不建立重叠订阅。
5. **回到正确原聊天。** 宿主通知适配器确认原聊天和所属主机；忙碌时等待合适续接点。状态区分执行中、结束待验收、已验收和需处理。关闭/归档/切换项目时不误投其他聊天。
6. **处理重启与未知投递。** 持久化通知拥有者、批次和投递/接收状态。正常完成只通知一次；响应丢失或结果未知时不宣称严格 exactly-once，也不盲目重发。恢复只附着原任务，不重新执行。
7. **按执行工作区验收。** 唤醒内容提供经过校验的任务引用；主脑一次取回交付包，到真正修改的工作区检查文件、测试和差异，按原责任记录验收。不同工作区的合并/部署仍是独立操作。

## 验收场景

- 原项目 A 聊天派发给工作区 B，完成通知只回 A 的原聊天，记录仍归 B。
- 两个聊天、两个工作区同时运行，不串任务、回执、订阅或验收权限。
- 单批次多个任务全部结束后只正常通知一次；失败、取消、待恢复如实显示需处理。
- 等待期间不发主脑模型请求；后台监听本身不等于模型推理。只报告实际观测，不承诺整个宿主绝对零用量。
- 原聊天忙、关闭、归档，宿主/工作台重启、通知响应丢失时，不误投、不重派、不擅自取消执行任务。
- 越权跨项目订阅、伪造聊天/工作区归属、旧引用和未知身份被拒绝；原同项目通知仍可用。
- mock 验证身份和故障分支；真实宿主验证主脑退出轮次后的原聊天续接。仅同步 wait 或探针接口返回成功不能算自动唤醒验收。
