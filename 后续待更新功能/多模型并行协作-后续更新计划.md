# 多模型并行协作：后续更新计划

整理日期：2026-10-18。

当前状态：本文件只整理讨论结论和建议实施顺序，不代表并行功能已经开始开发。作为前置收尾的 Agent 设置入口调整已于 2026-10-18 完成独立验收。

**目标**

用户提出需求后，由 GPT 主脑判断是否值得并行，必要时拆成可分别验收的任务，按模型能力、任务难度、上下文容量和成本分派。各执行模型完成调查、实现、自测和修正；主脑负责关键决策、独立验收及最终集成。目标是缩短独立任务的总耗时，并控制主脑协调开销；不预先承诺提速或额度节省比例。

**已经确定的方向**

- 每个模型保存自己的执行 Agent。目前本地 Qwen → Pi、DeepSeek → DSH；已有任务、续接、整改和恢复保持原 Agent，不随默认值迁移。
- 协作区域改为“选择模型 → 选择执行 Agent → 保存”。去掉界面上的全局默认 Agent 选择，后台保留旧配置兼容；参数入口统一叫“各执行 Agent 参数设置”。这项界面调整已完成并通过独立验收。
- 并行由主脑按需求判断，不强制拆分，不强制用满全部模型。不因空闲就把任务交给能力不合适的模型。
- 不同可用模型的数量决定并发上限；初版每个模型最多执行一项任务。重复别名不重复增加能力，共享同一本地推理资源时需保守限制并发。
- 无依赖的任务并行，有依赖的任务分轮执行。前置成果通过独立验收后，依赖任务才能启动。
- 同一项目的并行修改优先采用独立工作区。执行成果经过受控合并和集成测试，再进入用户项目。
- 复用现有批量后台等待：同一批次完成后集中唤醒、验收。完成通知不等于验收通过；异常仍要明确显示需要处理。
- 保留项目隔离、记录保护、付费授权、模型范围、预算与请求限制开关、无限总运行时长和一次自动整改上限。不会为并行而绕过原有门禁。

**当前已有基础与缺口**

已有：独立任务和会话记录、每模型 Agent 默认值、路由能力与费用检查、阶段依赖及哈希交接、批量完成监听、独立验收记录。

缺口：服务端仍是全局单任务执行队列；同项目运行中禁止再次派发修改任务；尚无任务工作区和受控集成生命周期；开启金额限制时，现有待结算费用处理需要适配并行；主脑尚未形成完整的并行拆分与批次分派规则。

**建议实施顺序**

| 顺序 | 更新内容 | 完成标准 |
| --- | --- | --- |
| 0 | 已完成：现有 Agent 入口调整并验收 | 快捷入口只保存选中模型的 Agent，轮询不吞未保存选择；刷新保留；参数入口改名；实际模型和全局设置不被误改。2026-10-18 独立验收通过。 |
| 1 | 明确并行决策和任务交接规则 | 每项任务有独立目标、文件/资源范围、接口约定、依赖、候选模型与验收标准；判断不值得拆分时直接串行。 |
| 2 | 建立独立工作区和受控集成流程 | Git 项目可从明确基线创建任务 worktree；成果可检查、试合并和集成验收；失败保留成果，不能直接覆盖用户工作目录。 |
| 3 | 建立并行调度与资源占用机制 | 不同模型可同时运行，同模型排队；重复模型/共享本地资源受约束；冲突任务等待；取消、失败和恢复不会重复执行或遗留占用。 |
| 4 | 完成费用和权限的并行校验 | 同时发请求时原子处理费用及待结算额度，限制生效时不能超支或误拒正常并行；关闭可选限制时维持用户原意。校验通过前不启用线上并行。 |
| 5 | 接入主脑自动评估、拆分和整批分派 | 由主脑决定并行组与执行轮次，按能力/难度分派；新任务遵循各模型默认 Agent；阶段依赖、验收和整改规则继续有效。 |
| 6 | 完善批次状态和一次完成唤醒 | 界面区分运行、排队、等待依赖、等待集成、待验收和需处理；同一批次采用一个监听订阅，避免逐任务唤醒主脑。 |
| 7 | 完成独立回归、受控部署和使用说明 | 离线并发与临时 Git 项目测试覆盖关键边界；工作台空闲时部署；分别确认独立任务能并行、冲突任务会等待、合并后的整体功能通过验收。 |

步骤 2—4 可以分别实现和离线验证，但必须全部通过独立验收后才能切换线上执行队列；不能先开放并发，再补成果和费用保护。

**初版范围与边界**

- 优先支持有 Git、基线明确、任务相互独立的项目。没有 Git 或不能安全确定基线时保守串行，不自动初始化 Git。
- 用户的未提交改动必须受到保护；不能为了并行擅自提交、暂存、重置或覆盖它们。
- 记录所属项目与任务实际执行目录需要分开管理。worktree 是执行副本，历史、日志、验收和交接仍归属可信的原项目，不能错误初始化另一套项目身份。
- 每个任务单独工作区、会话和必要的临时运行资源。工作区代码和业务成果不得放进 `.model-desk`；工作台记录仍由控制器维护。
- Git worktree 是版本工作区隔离，不是操作系统安全沙箱。共享端口、数据库、依赖安装及外部副作用需要额外约束；不能因为文件不同就直接放行。
- 成果应在独立集成工作区逐项合并。文本冲突或业务冲突由主脑判断；无法可靠解决时转为串行或记录受阻，不强行覆盖。
- 初版暂不做无 Git 项目的自动快照回写、复杂自动分支合并策略、多个模型重复竞争同一任务或强制自动扩满并发。是否采用容器作为统一执行环境另行评估，不作为直接兼容现有 Windows DSH/Pi 的既定结论。

**重点验收场景**

1. 两个合格模型的独立任务确实同时执行；同模型任务仍排队，重复配置不会额外占用一条并发能力。
2. 同一基线的两个工作区互不覆盖；同文件冲突会被检测；用户未提交改动不丢失。
3. 文件能够合并但接口不兼容时，集成验收能阻止错误成果进入用户项目。
4. 原始项目与工作区路径不同的情况下，记录、通知、续接、验收和交接仍归属正确项目。
5. 多项付费请求同时启动时账本一致、原有限制有效；不得自动改变用户关闭的金额或请求次数上限。
6. 取消其中一项不影响其他任务；失败、服务重启和恢复不重复派发，运行资源与占用能正确处理。
7. 依赖任务在前置独立验收前不能启动；同一批次正常完成后集中通知一次，交付结果逐项验收。

回归使用临时项目、临时记录、mock provider 和可控阻塞/并发事件，不调用真实模型。必要的实跑验证与离线回归分开记录，不以执行模型自述替代证据。

**已查阅的参考做法**

- [Git worktree](https://git-scm.com/docs/git-worktree)：独立任务工作区的基础机制。
- [Git merge](https://git-scm.com/docs/git-merge)：基于共同基线的合并与冲突报告。
- [Git merge-tree](https://git-scm.com/docs/git-merge-tree)：不修改工作目录和索引的合并预检机制。
- [OpenHands Docker Sandbox](https://docs.openhands.dev/openhands/usage/sandboxes/docker)：Agent 命令执行环境隔离的参考。采用容器仍需正确划分可写挂载，不能共同挂载同一原项目后宣称无冲突。

这些机制提供工作区、合并和执行环境的基础，不保证业务逻辑自动兼容。最终质量仍由主脑独立审查和合并后的集成测试确认。
