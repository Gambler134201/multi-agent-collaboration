# 多主脑 Agent 与模型适配：可行性与更新计划

整理日期：2026-10-18。

当前状态：2026-10-18 用户确定优先实施本功能，先梳理步骤；本轮重新核对了本地接口及三家官方接入文档，并细化下方计划，尚未改动运行逻辑。DSH、ZCode、WorkBuddy 作为主脑的完整流程均尚未端到端实测。本文是实施计划，不代表这些产品已经完成接入。

**功能目标**

让用户能够在不同主脑 Agent 和模型中使用同一套协作框架。主脑负责需求理解、任务拆分、路由、指导和独立验收，执行模型负责调查、实现、自测和修正。

用户可以选择当期有合适额度、套餐或活动权益的主脑入口，减少对单一 GPT/Codex 额度的依赖。是否能使用某项权益，需要按该产品的账号、入口和具体政策确认；不预设桌面端、CLI、开放 API 与普通模型 API 的额度互通。

**概念区分**

| 层级 | 职责 | 示例 |
| --- | --- | --- |
| 主脑 Agent／宿主 | 提供聊天、工具调用、会话、项目和账号入口 | 当前 Codex；计划研究 DSH、智谱 ZCode、腾讯 WorkBuddy |
| 主脑模型 | 承担需求理解、规划、判断和验收 | 所选宿主官方支持的 GPT、DeepSeek、GLM 等模型 |
| 执行 Agent | 承载执行任务、工具和执行会话 | 当前 DSH、Pi |
| 执行模型 | 完成分派任务中的调查、实现、自测和修正 | 本地 Qwen、DeepSeek 等已配置模型 |

同一个产品或模型可以在不同任务中承担不同角色。例如 DSH 既可以作为主脑宿主，也可以承载执行任务；两者的配置、会话、权限和验收身份必须分开。新增 DSH 主脑，不等于允许 DSH 执行端验收自己的成果。

主脑模型通常由宿主的模型选择机制决定，不需要为每个模型复制一套框架。但模型、提供商和具体版本仍需记录与验证；模型选择范围受宿主官方支持约束。

**已经完成的分析**

1. 核对三类产品的官方 MCP、插件或自动化接口，确认存在基础接入路径。
2. 确定采用“一套通用核心 + 各宿主差异适配”，避免为每家复制整套后台。
3. 区分基础任务协作与完整后台唤醒：接通 MCP 不等于已经实现原聊天自动继续。
4. 明确额度应按原生宿主入口使用和记录，不能把福利额度默认当成通用 API 余额。
5. 明确主脑能力必须独立验证：连接成功不代表规划、纠错和验收质量达到当前 GPT 的效果。

**官方接口调查结论**

| 产品 | 已查到的官方基础 | 尚需验证 |
| --- | --- | --- |
| DeepSeek Harness | ACP 自动化、持久会话、模型选项和 MCP 工具接入；当前项目已有 DSH 执行端适配经验 | 当前安装版本的主脑工具调用、项目/会话身份、原生交互入口和完成后续接；执行端经验不能替代主脑端验收 |
| ZCode | 本地/远程 MCP、插件、Hooks 以及宿主模型连接机制 | 实际安装版本的配置加载、项目绑定、等待和原聊天唤醒；不同产品入口/版本的能力需分别确认 |
| WorkBuddy | MCP/CLI 连接器；开放平台另有本地助理消息、云端任务和 ACP 接口 | 本地连接器与原聊天对应关系、授权要求、原聊天唤醒；不能将云端会话 API 直接等同于桌面任意聊天的控制接口 |

以上是文档层面的接入依据，不是本机兼容性测试结果，也不是对当前福利额度的确认。

**架构方向**

通用核心继续负责模型注册、任务派发、路由、项目记录、阶段依赖、费用控制、交付结果与验收。主脑 Agent 通过统一工具入口调用这些能力。

需要新增面向主脑的明确工具，例如查询候选模型、预览/派发任务、取得交付结果、读取必要上下文、提交独立验收或整改。不要直接将现有面板专用代理当成已经完成的跨宿主主脑接口；应保留原有鉴权、项目绑定和请求门禁。

各宿主适配层只处理差异：安装与连接配置、协作规则加载、可信项目与会话身份、完成通知/会话继续、额度读取、可用 UI 入口。基础工具共用，宿主差异按需补充，最后逐家验收。

内嵌面板不是通用接入的前提。宿主缺少相应 UI 能力时，可提供浏览器工作台或结构化结果；不能把某家特有的面板入口作为所有主脑的硬性依赖。

**当前代码中需要解除的宿主绑定**

- 协作规则安装当前面向 Codex 的配置和指令目录。
- 现有 MCP 服务主要服务工作台打开和面板请求代理，尚未形成完整通用主脑工具集。
- 完成通知依赖当前 Codex 聊天身份和桌面桥接；`desktop_notify.py` 与 `completion_wait.py` 的宿主依赖需要明确分层。
- 额度入口主要面向 GPT/Codex。新增主脑后需要区分当前宿主额度和执行模型 API 账单。
- 项目和会话绑定不能依赖服务安装目录、另一个标签页或全局最近项目。

现有 MCP、CLI 和 DSH 执行端代码是可复用基础，但不计为已经完成新主脑接入。

**后续更新步骤**

采用“一套现有核心 + 最小通用工具 + 各宿主薄适配”。先让一个新主脑完整工作，再推广到其他宿主；不重写工作台，不为每家复制任务/费用/验收系统，也不在本轮同时开发多模型并行。

| 顺序 | 待实现部分 | 完成标准 |
| --- | --- | --- |
| 1 | 核对宿主实际版本、入口和能力 | 记录 DSH、ZCode、WorkBuddy 实际安装情况与目标使用入口，核对 MCP、项目/会话来源、规则加载、等待和通知能力。优先做不提交模型轮次的握手/只读检查；缺少安装时明确待验证，不擅自安装或覆盖配置。历史探测报告不当作当前版本证明。 |
| 2 | 先确定项目、会话和角色归属 | 定义宿主、宿主版本、主脑模型、项目、会话及能力状态的最小约定；由受信启动上下文或明确用户绑定建立归属，模型猜测或传入一个项目字符串不等于完成可信绑定。模型身份区分声明与核实，读不到时保留未知。执行端不能因改一个 actor 字段就获得主脑验收权限。 |
| 3 | 开放最小通用主脑工具 | 先做候选模型查询、路由预览、派发、状态/交付取回、验收/整改这几类必要操作；复用现有后台或 CLI，不公开任意面板请求或命令执行接口。初始化/发现不自动启动工作台或执行模型；派发快速返回原任务 ID，长任务不占一个无限时 MCP 调用。对重复请求、超时和返回未知明确处理，不能盲目重派。 |
| 4 | 验证共用核心并保护当前 Codex 流程 | 用 mock 宿主、临时项目和记录验证工具闭环；回归现有 MCP 面板、项目隔离、每模型 Agent 默认值、费用门禁、依赖交接、独立验收和一次整改限制。旧任务不迁移身份或 Agent，当前 Codex 的打开面板和完成通知仍可使用。 |
| 5 | DSH 作为首个新增主脑跑通基础闭环 | 安装最小连接配置与协作规则，验证“DSH 接收需求 → 查询/选择执行模型 → 派发 → 获取交付 → 独立检查 → 通过或退回整改”。首个新宿主用于发现通用接口遗漏；能调用工具但不能正确拒绝缺陷交付，不算通过。DSH 主脑与 DSH 执行端的会话和权限分开。 |
| 6 | 拆出宿主通知差异，验证等待与唤醒 | 将 Codex 专用通知保留为一个适配实现，任务完成判定与结果取回继续共用。逐家验证能否回到正确原聊天；区分执行中、执行结束待验收、已通过和需处理。正常批次以一次完成通知为目标；未知投递不自动重发或重派。没有可靠官方续接能力时明确标注受限，并提供取回原任务结果的方式，不宣称已实现自动唤醒。 |
| 7 | 依次接入 ZCode、WorkBuddy | 复用已验证工具，只补各自 MCP/连接器配置、规则加载、可信项目与会话来源、等待及通知差异。每家先验收基础闭环，再单独验收原生入口与唤醒；发现缺能力只给该宿主标记限制，不能回头复制后台或削弱共同门禁。 |
| 8 | 补齐使用入口、额度展示和发布说明 | 清晰显示当前主脑宿主/模型及支持范围；主脑仍由用户在原生入口选择。宿主额度与执行 API 费用分开，缺官方查询能力时显示未知/由宿主查看。给出安装、项目使用、等待、恢复、明确交接及卸载/回滚说明，记录逐宿主/版本验收结果。 |

主脑身份和项目/会话归属放在派发接口之前处理，不推迟到跨宿主切换时补。第一版不做自动挑选优惠主脑、聊天历史自动同步、多个主脑同时指挥同一任务或自动跨宿主接管；后续明确交接必须校验目标、任务、原项目和实际文件基线，并记录新的责任归属。

**分阶段交付与验收**

- A：步骤 1—4 完成。交付接口约定、最小工具和离线回归；当前 Codex 兼容。此时不能标记任何新增主脑已接入。
- B：步骤 5 完成。DSH 基础协作闭环通过；若仍需手动取回，明确写为“基础可用，自动唤醒待验证”。
- C：步骤 6 在 DSH 上完成。验证后台等待、一次正常完成通知、正确原聊天续接与异常处理；不能用接口自测替代真实宿主验证。
- D：步骤 7—8 完成。ZCode、WorkBuddy 分别交付各自通过验收的能力和安装说明；主脑额度展示以真实支持范围为准。

每个宿主都应有一份小而共用的验收任务：正确交付可接受、故意带缺陷交付会被拒绝、运行中不会误判完成、断线不重复派发、切换项目不串记录。离线回归先用 mock，不消耗真实模型；必要实跑单独记录模型、版本和费用。原生入口及原聊天唤醒需要在实际宿主中验证。

**本轮核对到的具体依据（2026-10-18）**

- 本地 `codex_mcp_server.py` 仍以 `open_model_desk` 和应用专用 `panel_request` 为入口；不应直接把面板专用代理暴露给任意主脑当通用工具。
- `completion_wait.py` 直接依赖 `desktop_notify.py`；后者读取 Codex 当前聊天与桌面桥接身份，必须抽出宿主差异后再复用。
- [DSH 官方 ACP 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/acp/acp/README.zh.md)提供自动化会话与 MCP 接入，但明确限制交互 UI；官方主分支能力不能代替本机版本验证。
- [ZCode MCP 文档](https://zcode.z.ai/cn/docs/mcp-services)有本地 stdio 和项目/用户作用域；实际接入时需注意原生配置与兼容配置的覆盖优先级，保留原有其他服务。
- [WorkBuddy 连接器文档](https://open.workbuddy.cn/docs/connector)支持本地 stdio，并建议单次工具请求在 30 秒内响应。因此采用“快速派发返回 ID + 后台执行 + 按能力取回/通知”的通用路径，不把长任务运行时长等同于工具连接超时。Open API 页面本轮未成功取得，不据此增加自动唤醒能力承诺。

**主脑模型与福利额度的使用原则**

- 优先由用户在相应产品的原生入口选择主脑及模型，再连接本框架；按该产品官方允许的方式使用账号权益。
- 桌面账号权益、编程套餐、开放 API 和普通模型 API 的适用范围需分别核对，不能只凭同一个厂商品牌就视为通用额度。
- 不提取客户端登录凭据充当其他接口的通用密钥，不依赖未公开的私有接口作为正式适配方案。
- 初版由用户明确选择主脑，不自动根据活动或额度在不同宿主/模型间切换；自动切换与跨宿主无缝恢复不属于首版既定范围。
- 不承诺所有模型都具备当前 GPT 主脑同等的质量；主脑能力检查与任务验收独立于优惠价格和剩余额度。

**重点验证场景**

1. 正确识别原项目；项目不明确时保持未绑定，不能猜测为工作台安装目录或上次使用项目。
2. 主脑能够查看候选模型，按任务能力选择执行端，并遵循所选模型保存的默认执行 Agent。
3. 执行完成后主脑读取实际交付和必要证据，不把执行模型的“完成/测试通过”自述直接当成验收。
4. 提供带缺陷或接口不兼容的交付时，主脑能够拒绝或正确要求整改，而非一律通过。
5. 主脑与执行端角色分离；新增宿主不能弱化执行端自验收限制、项目记录保护或权限控制。
6. 后台通知只回到已确认的所属聊天与项目；会话关闭、切换或投递结果未知时，不误投递、不重复派发。
7. 模型和宿主切换后，历史任务、会话及费用仍保留真实原身份；任务仍由明确归属的主脑验收，不静默迁移。
8. 宿主额度与执行费用分别展示；无法读取时明确未知；不会更改现有付费授权、模型范围和用户关闭的可选费用/请求限制。

回归优先采用 mock 宿主、临时项目与记录验证接口和边界。真正的原生入口、唤醒、账号权益与模型判断质量，需要在具体宿主/版本中分别验证，不能由接口自测推定。

**与多模型并行计划的关系**

通用主脑接口与宿主能力边界宜先确定，供后续并行批次共享。新主脑基础接入不必等待并行功能全部完成；并行调度、独立工作区和受控集成仍按[多模型并行协作更新计划](多模型并行协作-后续更新计划.md)单独实施和验收。
