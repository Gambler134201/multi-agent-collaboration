# 开源多 Agent 项目调研与采纳建议

调研日期：2026-10-23。状态：调研完成，建议待实施；没有安装第三方框架、调用真实模型或改动产品运行逻辑。

本次将其他项目的官方说明、选读源码与我们自己的代码复盘分开记录。外部能力尚未在本机安装实测；来源里的支持列表、性能宣传不能当作我们的验收结果。网页和 main 分支会变化，实际引入代码或依赖前须固定版本、核对许可证与兼容性。

对应实施清单：[协作核心可靠性与并行能力更新路线](协作核心可靠性与并行能力更新路线-20261023.md)。既有[多模型并行计划](多模型并行协作-后续更新计划.md)与[多主脑计划](多主脑Agent与模型适配-可行性与更新计划.md)继续有效，本文件补充参考依据，不将计划改写为已完成功能。

2026-10-23 复核修订：这里的“建议采纳”指补足已有机制，不表示整项功能尚不存在。我们已有请求去重、预检、独立验收、交付包、交接哈希、阶段门禁、批次通知、质量校准查询及范围代码索引。哪些已有、哪些只差边界，见更新路线的能力对照表；不得据原版阶段标题重复开发。新增[项目地图专题](项目地图-参考与增量方案-20261023.md)，明确区分外部实际功能与本项目设计建议。

## 1. 结论与选型范围

最值得采纳的是：明确的任务与交付结构、按任务保存执行进度、可解释的失败信息、独立工作区、可查询的请求结果，以及可离线复现的诊断材料。

现阶段优先在现有控制器上逐项补齐，不整体迁移框架。我们的主脑来自 Codex、DSH 等不同宿主，执行端包括 Pi、DSH、WorkBuddy；原生登录权益、工具授权、工作台启动、项目绑定和原聊天唤醒都有宿主差异。通用编排库不能据此推定已兼容这些入口。

| 参考项目 | 查阅范围 | 最值得参考的部分 | 对我们的判断 |
| --- | --- | --- | --- |
| Agent Orchestrator / Orchestrator.inc | 官方 README、工作区与 Agent 适配文档 | 任务独立分支/worktree、执行会话与检查状态关联、能力与就绪状态分离 | 与现有产品形态最接近，优先参考 |
| LangGraph | 官方 checkpoint 文档、`PregelRunner.commit` 源码 | 按节点持久化结果，恢复时保留已成功节点 | 参考进度恢复机制，不能等同于外部副作用只执行一次 |
| CrewAI | 官方 Tasks、Processes、Flows 文档及 `Task` 源码 | 任务输出结构、校验函数、显式上下文、管理与执行分工 | 采用结构与校验思想，保留我们的独立验收与一次自动整改上限 |
| Microsoft Agent Framework | 官方 README、工作流与 checkpoint 文档 | Executor/流程分离、不同编排模式、可恢复工作流 | 用于梳理接口边界，不立即新增整套运行依赖 |
| OpenHands Software Agent SDK | SDK README、Task Tool Set、权限与持久化文档 | 工具/工作区/会话分层，动作分析与确认策略分离 | 参考工具事件与权限设计；同步子任务机制不替代我们的后台等待 |
| MetaGPT | 官方 README | SOP 与按阶段交付制品 | 参考交付模板，不把每个小任务扩成完整“软件公司” |
| Raven | 本轮重查轨迹诊断文档；此前已读部分编排源码 | 诊断包、录制结果回放、失败变回归用例 | 高优先级参考；回放不等于重新评估模型质量 |

AutoGen 另做维护状态核对：其官方 README 当前有归档及停止维护声明，并引导新用户使用 Microsoft Agent Framework。因此将 AutoGen 留作历史设计参考，不建议本次新增依赖。来源：[AutoGen README](https://github.com/microsoft/autogen/blob/main/README.md)。

## 2. Agent Orchestrator：最接近我们实际需求

官方将一个 worker 的任务、会话、工作区及源码检查状态关联起来；Git 项目使用独立分支和 worktree。适配文档同时区分终端、结构化聊天、Reviewer 能力，以及本机实际就绪状态。来源：[项目介绍](https://github.com/OrchestratorInc/agent-orchestrator)、[工作区](https://docs.orchestrator.inc/plugins/workspaces/)、[Agent 适配](https://docs.orchestrator.inc/plugins/agents/)。旧 ComposioHQ 仓库入口已重定向到 OrchestratorInc。

**建议采纳：**

- 将执行端描述拆成“支持什么”与“现在能不能用”：已安装、通道可用、原生模型可选、认证状态可确认、文件/终端能力、恢复与取消支持，各项独立表达。未知保持未知，不为了探测而读取认证文件或发送模型请求。
- 原生 CLI/协议存在时优先走受支持的机器接口；DSH 的 ACP 接入可作为适配参考。WorkBuddy 仍需要自己的原生通道，不能因别的 Agent 支持 ACP 就宣称它自动兼容。
- 并行任务绑定统一执行包：原项目、任务 ID、基线、执行工作区、原生会话、变更、独立验收、集成结果。
- 工作区管理集中在一个可见位置，保守清理，提供预览和保留原因；避免再次在用户项目父目录散落大量难辨认文件夹。

**不直接照搬：**外部项目某种 Pi 适配要求 bypass permissions，不构成修改我们权限模式的理由；采用协议也不等于默认完全访问。worktree 只隔离版本文件，端口、数据库、账号和浏览器资源仍需单独管理。

## 3. LangGraph：保存进度，让恢复有依据

官方说明 checkpoint 和节点级 pending writes，使同一步骤中已成功节点的结果可在恢复时保留。选读的 `PregelRunner.commit` 将成功写入、错误和中断分别交给 checkpointer。来源：[Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)、[Runner 源码](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/pregel/_runner.py)。

**建议采纳：**把“已生成文件、验证完成、执行结束、主脑验收、集成完成”分别记录，恢复时核对每步的真实证据，而不是重新执行整个批次。已验收且制品版本未变化的前置任务不因其他任务失败而重新调用模型。

**关键限制：**图状态被保存，不等于文件写入、发消息、外部 API 等副作用与 checkpoint 原子提交。我们仍需要 request_id、原生任务引用、结果核对和明确的 unknown 状态；不能把框架重试策略直接用于结果未知的模型请求。

本项目已经有阶段依赖、任务记录和哈希交接，改进应扩展这些机制，不另建一套互相矛盾的任务账。

## 4. CrewAI：任务契约与输出校验

Tasks 支持结构化输出、任务上下文和 guardrail 校验；Processes 区分顺序执行与管理者协调。`Task` 源码也显式处理输出结构和 guardrail 重试。来源：[Tasks](https://docs.crewai.com/en/concepts/tasks)、[Processes](https://docs.crewai.com/en/concepts/processes)、[Flows](https://docs.crewai.com/en/concepts/flows)、[Task 源码](https://github.com/crewAIInc/crewAI/blob/main/lib/crewai/src/crewai/task.py)。

**建议采纳：**

- 派发时形成明确任务契约：目标、范围、接口、依赖、允许的工具、制品和可判定验收条件。
- 执行端返回版本化结果结构，而不是靠中文答复或关键词推断成功、权限失败或预算失败。
- 先做不调用模型的确定性校验，再由主脑独立核验实际文件与测试。结构正确只能证明字段合规，不能证明业务正确。
- 条件任务需明确“未满足依赖”“主动跳过”“取消”，不把没执行显示成成功。

**不直接照搬：**外部 guardrail 的重试次数、管理者的判断、模型型校验器都不替代我们的权限与验收制度。校验可作为证据来源之一；保留最多一次自动整改，不能因引入框架扩大重试或循环付费。

## 5. Microsoft Agent Framework：编排核心与执行器边界

官方提供顺序、并发、交接等编排模式及工作流 checkpoint；文档描述在 superstep 边界保存执行器状态和待处理消息等内容。来源：[仓库](https://github.com/microsoft/agent-framework)、[工作流能力](https://learn.microsoft.com/en-us/agent-framework/workflows/)、[Checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)。本轮未安装实测。

**建议采纳：**公共编排核心管理项目身份、请求、阶段、预算与验收；执行端适配器管理自身的探测、会话、运行、工具事件和收尾。启动、取消、恢复、交付不能继续散落在越来越多的执行端条件分支里。

适配器应有统一契约测试：同一套测试输入，Pi、DSH、WorkBuddy 都能返回一致的状态含义。原聊天唤醒、账户来源、原生权限仍是适配器特性；没有对应实现就显示不支持，不能靠通用接口名称补齐。

## 6. OpenHands：工具事件、权限和会话分层

SDK 将工具、会话和工作区分开；权限文档区分动作风险分析与确认策略。Task Tool Set 明确是同步阻塞子任务，并非异步批次调度。来源：[SDK](https://github.com/OpenHands/software-agent-sdk)、[权限](https://docs.openhands.dev/sdk/guides/security)、[Task Tool Set](https://docs.openhands.dev/sdk/guides/task-tool-set)、[会话持久化](https://docs.openhands.dev/sdk/guides/convo-persistence)。

**建议采纳：**

- 权限检查先产生结构化事实：动作类型、已解析目标、规则编号、允许/拒绝/无法确认及原因，再由界面翻译成人能看懂的信息。
- 原始命令哈希继续用于核对；同时保存可脱敏的规则事实，解决过去“知道被拦了，却无法说明是哪类目标触发”的问题。不能因此默认保存完整私有会话、命令环境或认证内容。
- 将业务文件交付、自测、会话关闭、非必要临时清理分开显示；保留原始失败，不因文件存在自动验收。
- 验证临时文件尽量限定到任务专属目录；清理是独立、可选的收尾步骤，不把清理失败与业务验收混为一个状态。

**不直接照搬：**模型风险评分或提示词不是 OS 沙箱，完整会话持久化也不是我们的默认采集策略。其同步子任务不能替换我们“结束主脑回合、后台监听、回原聊天”的已验证路径。

## 7. MetaGPT：只借鉴适量 SOP

官方将需求、架构、实现等角色与 SOP 串联，强调按过程交付制品。来源：[MetaGPT README](https://github.com/FoundationAgents/MetaGPT/blob/main/README.md)。本轮只核对 README，没有据此声称其所有流程、集成或故障路径已审计。

**建议采纳：**为常见任务提供轻量交付模板：网页任务交付入口、运行方法和验证证据；接口任务交付接口约定和回归结果；调研任务区分事实、来源、推断与未验证项。

仅在任务需要时增加角色。小任务不强制经过产品经理、架构师等多个模型；重要的是接口、制品和验收条件完整，不是对话人数多。

## 8. Raven：诊断回放与测试样本

轨迹工具把失败及相关材料打包，并可用录制的模型/工具结果驱动回放，不重新运行真实工具。原始包未自动脱敏，分享流程单独处理脱敏。来源：[Trajectory debugging and replay](https://evermind-ai.github.io/Raven/trajectory-debugging/)。

**建议采纳：**每次典型故障生成最小诊断包，并沉淀成离线回归样本。先覆盖回执丢失、权限拒绝、原生会话未就绪、验证阶段失败、收尾异常和通知确认等已有问题。

导出默认使用本项目的最小脱敏材料，不自动扫描第三方聊天、认证文件或密钥；分享前可预览，不自动上传。缺少事件就标记不可回放，不能仅凭哈希恢复旧命令。回放通过也不等于新模型质量通过，模型质量须另做受控基准。

## 9. 补充机制参考，不作为多 Agent 框架直接替换

- [Temporal 的幂等与持久执行说明](https://temporal.io/blog/idempotency-and-durable-execution)：提醒我们重试与业务副作用不是天然原子的。建议借鉴请求身份与结果确认，不立即引入 Temporal 服务，也不复制默认重试策略。
- [ACP 工具调用规范](https://agentclientprotocol.com/protocol/v1/tool-calls)：参考统一工具事件与权限请求；传输协议不能替代项目授权、记录保护和宿主账号验证。
- [A2A 任务生命周期](https://a2a-protocol.org/latest/topics/life-of-a-task/)：参考任务、上下文及终态分离；暂不将全套网络互通协议作为本机可靠性修复前置。
- [Git worktree](https://git-scm.com/docs/git-worktree)：用于代码副本隔离；不能解决语义冲突和共享外部资源。现有并行计划仍需独立集成验收。

## 10. 与本项目源码复盘的对应关系

以下是本项目代码检查结论，不是外部框架替我们验证的结果。基线为本地源码提交 `8927cfa`；历史任务没有被修改或批量审计。

| 现有位置 | 本地观察 | 对应改进 |
| --- | --- | --- |
| `.local-worker/brain_requests.py`、`panel_server.py`、`brain_transport.py` | 模拟“操作成功后收据保存失败”：存储异常未进入 `UnknownOutcome`；通用 HTTP 400 可被客户端解释为拒绝 | 优先补结果分类与只读请求找回，不因不确定结果重派 |
| `.local-worker/failure_classification.py` | 合成样本中，“权限/预算”业务错误可被关键词规则归入系统故障 | 结构化错误来源；历史推断与验证证据分开 |
| `.local-worker/panel_server.py`、`execution_engines.py` | 公共控制器含执行端分支，新增适配需要跨多处修改 | 渐进提取适配器与契约测试 |
| `.local-worker/workbuddy_worker.py` | 文件生成、自测、权限与关闭会话等失败最终影响同一执行结果 | 分维度展示交付与失败，原始状态保持 |
| `.local-worker/task_handover.py`、`delegation_policy.py` | 已有独立验收与交接哈希，但可进一步把验收绑定到当时制品版本 | 保存验收版本，区分历史通过与当前文件已变化 |
| `.local-worker/completion_wait.py` | 现有测试覆盖不重复通知、发送结果未知及快速确认竞态 | 保留已验证机制，不为换框架重写 |
| `.local-worker/context_manager.py` | 已有范围代码索引、符号/签名、哈希与刷新；Pi/DSH 已有接入调用 | 地图应在此基础上补关系与展示，不从零重建索引，不把它说成三执行端已全覆盖 |

上述收据与通知模块的既有 42 项离线测试已通过；新增模拟故障暴露的是测试覆盖外的边界，不代表历史故障已经归因。外部项目本轮均未做模型效果或性能对比，不能写成“引入后必然降本/提速”。

## 11. 采纳决策

优先：请求结果确认、结构化错误和交付、适配器契约、最小诊断包、验收制品版本、并行资源与工作区管理。

后置：大规模多 Agent 对话、自动角色膨胀、向量记忆、自动修改框架的演化器、全框架迁移、未经证明的完全自动合并。

实施必须同时检查 Codex、DSH 的公共行为；WorkBuddy 当前是执行端，其主脑适配另按原计划推进。新增执行端或新主脑通过协议握手，不等于原生工具、账户、独立启动或唤醒已经验收。
